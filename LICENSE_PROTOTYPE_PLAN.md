# Прототип для продажи лицензии — план и журнал

Контекст: у владельца появился первый потенциальный клиент, которому можно
продать не копию redevelopment.pro, а модульный продукт (закупки + шахматка
бронирования, выросшая из интерактивных планировок объекта). Обсуждали два
уровня архитектуры — временную (прототип, пока лицензию не купили) и целевую
(после покупки). Это план временного уровня.

## Решение по стратегии (2026-09-09)

- **Никакой мультитенантности сейчас.** Не трогаем RLS/auth текущей платформы,
  не вводим tenant_id. Полноценная модульная архитектура (общие пакеты/
  монорепо, автопропагация фиксов между вашей платформой и клиентской,
  white-label, авторизация под несколько клиентов) — откладывается **до
  реального факта покупки лицензии**. Сейчас это был бы overhead без выгоды.
- **Отдельная инфраструктура, минимальная.** Свой репозиторий, свой Supabase-
  проект, свой Vercel-проект/домен — не общий с `claude/redevelopment-
  platform-prototype-oodobu` (прод). Цель — прототип для демо/питча клиенту,
  не production-ready SaaS.
- Когда лицензия куплена — возвращаемся к обсуждавшейся целевой архитектуре
  (монорепо с `packages/*` + `apps/redevelopment` + `apps/<client>`,
  композиция вместо форка модулей, отдельные Supabase/Vercel на каждое
  приложение) — см. диалог с владельцем в сессии от 2026-09-09.
