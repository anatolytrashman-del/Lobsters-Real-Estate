Ключевые находки отчёта (в порядке вклада в оценку):

1. **Первый документ — 3,41 КиБ (сжатых).** Это пустой SPA-шелл, не пререндер.
   Контент появляется только после загрузки/выполнения JS → отсюда FCP 5,1 с
   и SI 7,7 с. LCP-картинка (`/images/district/hero-5.jpg`) тоже открывается

2. **Яндекс.Карты (`yastatic.net/.../release/full.js`, 689 КиБ)** — 2 174 мс

   неиспользуемого JS, forced reflow 147 мс, 370 дочерних узлов в DOM.
   Грузятся сразу при открытии страницы, хотя обе карты далеко внизу.
3. **Шрифты — 4 × ~109 КиБ TTF** (Regular/Medium/SemiBold/ExtraBold) на
   критическом пути (Network dependency tree: max critical path latency 655 мс —
   ровно шрифты). Исходники в `public/fonts/` — по 260 КБ каждый, TTF без
   сабсета.
4. **Яндекс.Метрика (`tag.js`, 87 КиБ)** — 796 мс CPU, 2 длинные задачи в
   окне загрузки (2,6–2,8 с), 42 КиБ неиспользуемого кода. Инициализируется
   инлайн-скриптом в `<head>` с `webvisor: true, clickmap: true`.
5. **Картинки — «Est savings 151 КиБ»**: логотипы PNG в 3–4 раза больше
   отображаемого размера (Dana Holdings 585×176 → 209×63; Happy Planet
   200×198 → 85×84; Минск Мир 171×200 → 54×63), hero-фото — JPEG без WebP,
   `/icons/minsk-metro-line3.png` — 640×302 / 72 КиБ для иконки высотой 16 px.
   У всех `<img>` нет `width`/`height`.
6. **Данные первичного рынка — 7 запросов к Supabase ×~40 КиБ = 253 КиБ**
   (`primary_market_offers?select=*&offset=0..6000&limit=1000`) — вся таблица
   (6 158 строк) целиком, последовательно, на каждое открытие страницы, ради
   5 строк сводной таблицы.
7. **Главный JS-чанк — 167 КиБ (сжатых), 71 КиБ не используется на этой
   странице**; отдельный `supabase-*.js` 53 КиБ, из них 43 КиБ не используется.
8. **Кэш**: Lighthouse пожаловался только на 3rd-party (Метрика/Карты), но
   по факту (curl -I) ВСЯ статика прода отдаётся с
   `cache-control: public, max-age=0, must-revalidate` — включая хэшированные
   `/assets/*.js`, шрифты и картинки. Для первого захода не важно, для
   повторных — каждый раз ревалидация всех файлов.
9. **Accessibility 86** — только контраст: `text-primary` (#e4152b) на светлом
   фоне («RED» в логотипе, ссылка «деловой центр Red One»), `text-ink-faint`
   (#9a9ba3) на `bg-bg`/белом (подписи «Категория бизнеса», «Квартал»,

## 1. Что нашлось сверх отчёта при проверке прода (2 реальных бага, не «оптимизация»)

- [ ] **Б1. Пререндер `/minsk/minsk-mir` не работает на проде** (и это главная
  причина п.0.1). Проверено `curl https://redevelopment.pro/minsk/minsk-mir` →
  8 477 байт, 0 `<img>`, нет `<h1>` — это `dist/index.html` (шелл) из общего
  rewrite `"/(.*)" → "/index.html"`. При этом `/minsk/one` → 48 КБ и `/minsk`
  → 12,7 КБ — пререндерены. Не пререндерены также `/minsk/bcminsk` и все
  `/minsk/bcminsk/<slug>` (8 477 байт каждая). То есть `scripts/prerender.mjs`
  на Vercel обрабатывает лишь часть путей и **молча** пропускает остальные
  (`renderPath` после 2 неудачных попыток пишет `console.error` и НЕ роняет
  сборку — см. комментарий в самом скрипте). Главный подозреваемый — коммит
  `b9c5311` «один браузер на сборку + пул из 4 воркеров» (журнал CLAUDE.md
  сам предупреждает про нестабильность браузера на билд-контейнере Vercel).
  Другой кандидат — `waitForSelector('h1', 20с)`/`waitForFunction('Загрузка…',
  15с)` на медленной странице (7 последовательных запросов к Supabase, см.
  п.0.6) на слабом CPU билд-контейнера.
- [ ] **Б2. Таблица «Вторичный рынок» на проде пуста для посетителей** — в
  отчёте Lighthouse видно «Данные пока не собраны.» (Accessibility-секция,
  блок `#market`). Причина: `fetchMarketOffers()` (`src/lib/marketOffersApi.ts:31`)
  делает `select('*')`, а после P0.2 аудита безопасности (2026-08-28) anon
  имеет колоночный `GRANT SELECT` на `market_offers` — `select=*` отдаёт
  `42501 permission denied for table market_offers` (проверено curl'ом с
  anon-ключом; `select=id` при этом работает, 780 строк). `DistrictGuidePage`
  ловит ошибку → `setMarketOffers([])` → «Данные пока не собраны». Со дня
  аудита публичная страница показывает пустую таблицу вторичного рынка, а
  пререндер-снапшот (когда он работал) её тоже не содержал. Тот же вызов из
  админки (`MarketOffersReview.tsx`, authenticated) работает — поэтому никто
  не заметил.

## 2. Этапы (в порядке выполнения — сверху максимальная отдача за минимум работы)

Оценки эффекта — ориентировочные, из структуры отчёта (сколько миллисекунд/КиБ
даёт каждый пункт), не обещание конкретного балла. Реалистичная цель после

После КАЖДОГО этапа: `npx tsc -b && npm run build` (см. §4 про то, что

не гадать, что сработало.

### Э0. Вернуть пререндер `/minsk/minsk-mir` (и остальных пропавших путей) — Б1

Самый большой рычаг: FCP/SI/LCP сразу упираются в HTML, а не в JS. Ожидаемо
FCP 5,1 с → ~1,5–2 с, SI 7,7 с → ~3 с, LCP 7,6 с → ~3–4 с (картинка hero
становится «discoverable in initial document» без JS).

- [ ] Э0-1. **Диагностика по логам Vercel** (нужен владелец — см. §5, В1):
  в Build Logs последнего деплоя найти строки `[prerender] /minsk/minsk-mir`
  и `[prerender] ... пропущен после 2 попыток` / `попытка 1 не удалась`.
  По тексту ошибки понять: «browser closed/crashed» (→ пул воркеров) или
  «Timeout ... waiting for selector h1» / «Загрузка… не исчезла» (→ страница
  слишком медленно грузит данные на билд-контейнере).
- [ ] Э0-2. **Сделать пропуск пререндера заметным.** В `scripts/prerender.mjs`

  падает, прод остаётся на прошлой версии, владелец видит красный деплой).

### Э8. Accessibility (контраст) — параллельно с любым этапом, отдельный коммит

## 3. Что НЕ делаем (и почему)

- **Не переезжаем на SSR/Next.js.** Пререндер (Э0) + клиентский рендер
  закрывает те же метрики для контентных страниц; переезд стека — недели.
- **Не убираем Яндекс.Карты и Метрику.** Только откладываем их загрузку
  (Э2/Э3) — функционал и статистика остаются.
- **Не меняем Montserrat на системный шрифт** — фирменный стиль; экономим
  форматом и сабсетом (Э1).
- **Не подключаем image-CDN/сервис ресайза** — картинок на странице
  ~10, все статичные, достаточно один раз пересохранить (Э4).
- **Не делаем Service Worker/офлайн-кэш** — избыточно для сайта-визитки,
  риск залипания старых версий после деплоя.
- **Не трогаем глобальные токены цвета в `index.css`** ради контраста
  (Э8) — это затронет всю админку; правим точечно на публичной странице.
- **Не оптимизируем `/admin/*`** — за паролем, PageSpeed туда не ходит.

## 4. Как проверять (в песочнице и на проде)

- Сборка: `npx tsc -b && npx vite build` — обязательно перед каждым
  коммитом. Полный `npm run build` в песочнице упирается в `prerender.mjs`
  (виснет на сети до Supabase — известно, см. журнал CLAUDE.md) — сам
  пререндер проверяется только на проде (Э0-5).
- Размеры чанков: `ls -S dist/assets/*.js | head` + `gzip -c … | wc -c`.
- Локальный Lighthouse (1st-party часть): `npx vite preview --port 4173` и
  `CHROME_PATH=/opt/pw-browsers/chromium npx lighthouse
  http://localhost:4173/minsk/minsk-mir --only-categories=performance
  --form-factor=mobile --chrome-flags="--headless --no-sandbox"
  --output=json --output-path=./scratchpad/lh.json`. Внешние домены
  (yandex, supabase) из headless-браузера песочницы заблокированы — цифры
  будут лучше прода, годятся только для сравнения «до/после» по 1st-party
  (шрифты, картинки, чанки), не как итоговая оценка.
- Итоговая оценка — только PageSpeed Insights на проде, владелец после
  каждого деплоя (мобильный + десктоп). Смотреть не на балл, а на
  FCP/LCP/TBT и список «Insights» — балл шумит на ±5 между прогонами.
- Визуальная проверка (карты, слайдер, таблицы) — мок-тест Playwright по
  обычному правилу проекта (временный роут, скриншот, откат).
