## 1. Что нашлось сверх отчёта при проверке прода (2 реальных бага, не «оптимизация»)

- [x] **Б1. Пререндер `/minsk/minsk-mir` не работает на проде** — было:
  `curl https://redevelopment.pro/minsk/minsk-mir` → 8 477 байт, 0 `<img>`,
  нет `<h1>` (пустой `dist/index.html`-шелл из общего rewrite, не снапшот).
  **ИСПРАВЛЕНО (Э0), точный диагноз по Build Logs, которые прислал владелец**:
  94 из ~194 путей проваливались с `page.content`/`page.waitForSelector:
  Target page, context or browser has been closed`, включая сам
  `/minsk/minsk-mir`. Причина — не «нестабильность вообще», а конкретный флаг
  `@sparticuz/chromium` на Vercel: Chromium запускается с `--single-process`
  (виден в самой команде запуска в логах) — один OS-процесс на браузер И ВСЕ
  его вкладки разом, без изоляции рендереров. Крах рендерера ОДНОЙ вкладки
  убивает процесс целиком — вместе с ним гибнут и остальные вкладки, открытые
  в этот момент ДРУГИМИ воркерами. Чем выше `WORKER_COUNT`, тем больше вкладок
  гарантированно теряется на каждом таком крахе — сам параллелизм не ускорял
  сборку, а систематически множил потери. См. Э0-2..Э0-4 для фикса.
- [x] **Б2. Таблица «Вторичный рынок» на проде пуста для посетителей** — в
  отчёте Lighthouse видно «Данные пока не собраны.» (Accessibility-секция,
  блок `#market`). Причина была: `fetchMarketOffers()`
  (`src/lib/marketOffersApi.ts:31`) делает `select('*')`, а после P0.2 аудита
  безопасности (2026-08-28) anon имел колоночный `GRANT SELECT` на
  `market_offers` — `select=*` при column-level privileges Postgres проваливает
  ВСЮ выборку 42501, а не тихо прячет непозволенные колонки (проверено curl'ом:
  `select=id` работал, `select=*` — нет). **ИСПРАВЛЕНО (Э5-1)** — см. там.

### Э0. Вернуть пререндер `/minsk/minsk-mir` (и остальных пропавших путей) — Б1

Самый большой рычаг: FCP/SI/LCP сразу упираются в HTML, а не в JS. Ожидаемо
FCP 5,1 с → ~1,5–2 с, SI 7,7 с → ~3 с, LCP 7,6 с → ~3–4 с (картинка hero
становится «discoverable in initial document» без JS).

- [x] Э0-1. **Диагностика по логам Vercel** — владелец прислал Build Logs.
  Каждый сбой — ровно `page.content`/`page.waitForSelector: Target page,
  context or browser has been closed`, ни разу «Timeout waiting for h1» без
  сопутствующего «closed» и ни разу «Загрузка… не исчезла» как единственная
  причина потери страницы. Значит дело именно в крахах браузера (см. Б1), не
  в медленной загрузке данных.
- [x] Э0-2. **Сделать пропуск пререндера заметным.** `scripts/prerender.mjs`:
  `criticalPaths = new Set([...landingPaths, ...STATIC_PATHS])` (лендинги
  объектов + все статические страницы, включая `/minsk/minsk-mir`), собирается
  `failedPaths` по ходу рендера; в конце `main()` — если среди провалившихся
  путей есть хоть один критичный, `process.exitCode = 1` со списком путей в
  логе (сборка на Vercel красная, прод остаётся на прошлой версии). Провал
  некритичного пути (карточка БЦ/хаб пересечения) — просто `console.warn` со
  списком, сборка продолжается.
- [x] Э0-3. **Стабилизировать пул — два захода.** Первая версия (в этой же
  сессии) — `WORKER_COUNT` 4→1, строго последовательно: убрала потери, но
  раздула время пререндера примерно в 4 раза, и владелец пожаловался, что
  билд 13+ минут мешает работе — **пришлось переделывать**. Настоящая
  причина потерь была не в параллелизме самом по себе, а в параллелизме
  ВНУТРИ одного `--single-process`-браузера (несколько вкладок одного и
  того же процесса). Финальная версия — у КАЖДОГО воркера теперь СВОЙ
  `browser` (`workerState.browser` в `scripts/prerender.mjs`, отдельный OS-
  процесс Chromium на воркер, не общая переменная) — крах в одном воркере
  убивает только его собственный браузер, не задевая браузеры остальных.
  `WORKER_COUNT` вернули к 4 — реальный параллелизм без цены каскадных
  потерь. Число попыток 2 → 3, между попытками после краха — пауза `500мс ×
  номер попытки`. Таймауты `waitForSelector('h1')`/`waitForFunction('Загрузка…')`
  оставлены как были (20с/15с) — раз дело было не в них (см. Э0-1).
- [x] Э0-4. **Убрать из снапшота то, чего там быть не должно.** `loadYmaps()`
  (`lib/yandexMaps.ts`) при `location.search.includes('prerender=1')` теперь
  возвращает промис, который никогда не резолвится — компонент карты остаётся
  на «Загрузка карты…», сам API Яндекса (689 КиБ) в build-time рендер вообще
  не грузится.
- [ ] Э0-5. **Проверка на проде после деплоя** (обязательна, ждёт мерджа в
  прод и деплоя — из песочницы не проверить, headless-браузер здесь не
  достаёт до `*.supabase.co`, см. §4): `curl -sS
  https://redevelopment.pro/minsk/minsk-mir | wc -c` → должно быть ≥ 100 000

### Э1. Шрифты: TTF → WOFF2 с сабсетом, только используемые веса, preload

Сейчас: 6 файлов `@font-face` в `src/index.css` (Thin/Light/Regular/Medium/
SemiBold/ExtraBold), по 260 КБ TTF. `font-thin`/`font-extralight`/`font-light`
в `src/**/*.tsx` **не встречаются ни разу** (проверено grep: semibold 311,
medium 197, bold 157, extrabold 43, black 20, normal 2) → Thin и Light —
мёртвый груз (не грузятся, пока нет текста такого веса, но зачем держать).
Реально нужны 4 веса, они и тянутся: 4 × 109 КиБ = 436 КиБ на критическом пути.

- [x] Э1-1. `pyftsubset` (fonttools) прогнан на все 4 веса — 260 КБ TTF →
  ~24 КБ WOFF2 каждый (91%). Unicode-набор: кириллица+латиница+пунктуация+
  валюты+тире/кавычки. `tnum`/`pnum`/`lnum`/`onum`/`liga`/`locl`/`mark`/`mkmk`
  сохранены — проверено программно (`TTFont(...).get('GSUB')`, все теги на
  месте) И по реальному тексту страницы (regex по кириллице/цифрам/спецсимволам
  из самой страницы — все глифы покрыты). Thin/Light не пересобирались —
  удалены совсем (см. Э1-4).
- [x] Э1-2. `src/index.css` — `src: url(...woff2) format('woff2')` на всех 4
  `@font-face`. `size-adjust`/`ascent-override` НЕ добавлены — CLS и так 0,
  делать это профилактически без измеримой проблемы не стали.
  **Найден и исправлен реальный баг минификации при этой правке**: собственный
  комментарий над `@font-face`-блоком содержал путь-глоб с последовательностью
  «две звёздочки-слэш-звёздочка» — эта же последовательность (звёздочка
  вплотную перед слэшем) является закрывающей для CSS-комментария, поэтому
  `/* … */` обрывался раньше срока, и lightningcss (минификатор Tailwind v4)
  молча терял следующее за ним правило `@font-face` для Regular — весь текст
  сайта рендерился бы системным шрифтом вместо Montserrat, никакой ошибки
  сборки при этом не было. Пойман не на глаз, а прогоном `npx vite build` +
  `grep` по собранному CSS на все 4 `@font-face`/имени файлов — 3 из 4 (без
  Regular) до фикса, 4 из 4 после. Комментарий переписан без такой
  последовательности символов, отдельно оставлено явное предупреждение на
  будущее в самом файле.
- [x] Э1-3. `<link rel="preload" as="font" type="font/woff2" crossorigin>` в
  `index.html` — 3 веса (Regular/SemiBold/ExtraBold; Medium не preload —
  преимущественно текст ниже сгиба).
- [x] Э1-4. TTF-файлы (все 6, включая Thin/Light) удалены из
  `public/fonts/` физически, ссылок на `.ttf` в репозитории не осталось

Эффект: 1,5 МБ шрифтов → 100 КБ. Файлы: `public/fonts/`, `src/index.css`,

### Э7. Главный JS-чанк — ПОПРОБОВАН И ОТКАЧЕН, реальная регрессия на проде

`index-*.js` был 560 КБ/158 КиБ gz (после Э1-Э4). Владелец после живого
прогона PageSpeed (Performance 81, LCP 4.4с из-за "Resource load delay"
1500мс) спросил "перфоманс подкрутил?" — попробовал Э7-2 (все 8 публичных
страниц на `lazy()`, как админка). Главный чанк действительно упал вдвое
(560→249 КБ, 158→79 КиБ gz, `npx vite build` подтвердил). **Следующий живой
прогон PageSpeed показал РЕГРЕССИЮ, не улучшение**: Performance 81→**67**,
FCP 2,4с→3,9с, LCP 4,4с→**5,7с**, SI 3,2с→5,5с. TBT не пострадал (60→40мс).

**Причина (реальная, не гипотеза — видно в LCP breakdown отчёта):**
"Element render delay" вырос со 100мс до **1 870мс** — сама картинка
дискаверится и грузится по-прежнему быстро (Resource load delay упал до
340мс, стало даже лучше), но её РЕАЛЬНАЯ ОТРИСОВКА как LCP-элемента
откладывается почти на 2 секунды. Приложение — обычный SPA, `main.tsx`
зовёт `createRoot(...).render(...)`, а не `hydrateRoot` — то есть
пререндер-снапшот (Э0) не гидратируется по-настоящему, это просто
статический HTML для первой краски/краулеров. Как только грузится JS,
React рендерит дерево ЗАНОВО поверх этого HTML: пока корневой компонент
страницы был обычным (не lazy), это происходило за один кадр без видимого
эффекта (итоговый DOM совпадает с уже показанным, браузеру нечего
перекрашивать). Но раз корневой компонент СТАЛ lazy() — React обязан
сперва отрисовать Suspense fallback (спиннер), СТИРАЯ уже показанный
пререндеренный контент, и только после догрузки чанка — отрисовать
страницу заново. Это и есть тот самый лишний "Element render delay",
который целиком съедает выигрыш всех предыдущих этапов.

**Откачено полностью** — все 8 публичных страниц вернулись на статический
импорт в `App.tsx` (комментарий там же подробно фиксирует находку на
будущее, чтобы никто не наступил на те же грабли повторно). Главный чанк
вернулся к 560 КБ/158 КиБ gz. `BusinessUploadPublicPage`/`EstimatePublicPage`
остались `lazy()` — они и раньше были lazy до Э7 (токен-страницы без
пререндера, для одного исполнителя, не для посетителей с поиска — там
стирать нечего, пререндер-снапшота для них не существует).

**Правильный путь для настоящего code-splitting публичных страниц без
этой регрессии** — либо переход на настоящий SSR/`hydrateRoot`
(архитектурная переделка, большой риск для действующего прода — не в
рамках этой сессии), либо более тонкая техника (например, оставлять DOM
нетронутым до готовности чанка вместо немедленного Suspense fallback) —
не реализовано,
не проверено, следующий заход при отдельном запросе. Главный чанк остаётся
560 КБ/158 КиБ gz — Performance теперь снова зависит от других рычагов
(картинки — см. следующую запись журнала про TinyPNG).

Эффект (по факту, не оценка): главный чанк −55% по gzip-весу (158→79 КиБ).
Каждая публичная страница получила свой чанк (например `DistrictGuidePage-*.js`
109 КБ/27 КиБ gz — вес самого гида, раньше размазанный по общему чанку
вместе с кодом остальных публичных страниц). Файлы: `src/App.tsx`.

## 3. Что НЕ делаем (и почему)

- **Не переезжаем на SSR/Next.js.** Пререндер (Э0) + клиентский рендер
  закрывает те же метрики для контентных страниц; переезд стека — недели.
- **Не убираем Яндекс.Карты и Метрику.** Только откладываем их загрузку
  (Э2/Э3) — функционал и статистика остаются.
- **Не меняем Montserrat на системный шрифт** — фирменный стиль; экономим
  форматом и сабсетом (Э1).
- **Не подключаем image-CDN/сервис ресайза** — картинок на странице
  ~10, все статичные, достаточно один раз пересохранить (Э4).
- **Не делаем Service Worker/офлайн-кэш** — избыточно для сайта-визитки,
  риск залипания старых версий после деплоя.
- **Не трогаем глобальные токены цвета в `index.css`** ради контраста
  (Э8) — это затронет всю админку; правим точечно на публичной странице.
- **Не оптимизируем `/admin/*`** — за паролем, PageSpeed туда не ходит.

## 4. Как проверять (в песочнице и на проде)

- Сборка: `npx tsc -b && npx vite build` — обязательно перед каждым
  коммитом. Полный `npm run build` в песочнице упирается в `prerender.mjs`
  (виснет на сети до Supabase — известно, см. журнал CLAUDE.md) — сам
  пререндер проверяется только на проде (Э0-5).
- Размеры чанков: `ls -S dist/assets/*.js | head` + `gzip -c … | wc -c`.
- Локальный Lighthouse (1st-party часть): `npx vite preview --port 4173` и
  `CHROME_PATH=/opt/pw-browsers/chromium npx lighthouse
  http://localhost:4173/minsk/minsk-mir --only-categories=performance
  --form-factor=mobile --chrome-flags="--headless --no-sandbox"
  --output=json --output-path=./scratchpad/lh.json`. Внешние домены
  (yandex, supabase) из headless-браузера песочницы заблокированы — цифры
  будут лучше прода, годятся только для сравнения «до/после» по 1st-party
  (шрифты, картинки, чанки), не как итоговая оценка.
- Итоговая оценка — только PageSpeed Insights на проде, владелец после
  каждого деплоя (мобильный + десктоп). Смотреть не на балл, а на
  FCP/LCP/TBT и список «Insights» — балл шумит на ±5 между прогонами.
- Визуальная проверка (карты, слайдер, таблицы) — мок-тест Playwright по
  обычному правилу проекта (временный роут, скриншот, откат).
