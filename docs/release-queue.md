# Очередь релиза

Накопитель готовой, но ещё не опубликованной работы. Владелец ведёт несколько
диалогов параллельно, каждый доводит свою фичу до готовности и **останавливается
перед публикацией**; потом всё накопленное уезжает в прод **одним мерджем = одним
билдом Vercel**.

Правила работы с этим файлом — в `CLAUDE.md`, раздел "Очередь релиза". Коротко:

- сессия дописывает СВОЮ запись в "Ждут публикации" сверху, на своей ветке,
  и на этом заканчивает — в `oodobu` ничего не пушит;
- публикующая сессия собирает все перечисленные ветки в одну релизную,
  прогоняет сборку и открывает ОДИН PR в `oodobu`;
- после публикации записи переезжают в "Опубликовано" (внизу), не удаляются.

Конфликт в этом файле при мердже (две сессии дописали сверху) разрешается как
в журнале — **сохранять обе записи**, не выбирая сторону.

## Ждут публикации

Формат записи:

```
### <ветка>
- **Что:** одна строка, что меняется с точки зрения владельца
- **Проверено:** чем (сборка, мок-тест, скриншоты, ручной прогон)
- **Миграции SQL:** применены / нет; какие именно
- **Риск при задержке:** есть/нет и какой
```

### claude/wonderful-einstein-vdg945 — ОТЛОЖЕНА ОСОЗНАННО
- **Что:** очередь повторной отправки одиночных писем (отказ Resend больше не
  теряет письмо): новая таблица `outgoing_email_jobs`, колонки `send_status`/
  `send_error` у `supplier_offer_emails` и `purchase_emails`, Edge Function
  `process-outgoing-emails`.
- **Почему не в релизе 2026-09-12:** в шапке её миграции
  (`supabase/migrations/20260912-outgoing-email-queue.sql`) прямым текстом:
  «эта миграция ещё НЕ применена к проду (владелец попросил не выкатывать до
  обновления тарифа)». Проверено запросом к базе — таблицы
  `outgoing_email_jobs` там действительно нет, то есть код бы поехал в прод
  и обращался к несуществующей таблице.
- **Что нужно для публикации (все три шага, по порядку):**
  1. обновить тариф Resend (ради этого и откладывалось);
  2. применить миграцию, затем задеплоить Edge Function
     `process-outgoing-emails`;
  3. только ПОСЛЕ деплоя функции раскомментировать и выполнить блок
     `cron.schedule` в конце той же миграции — иначе крон каждую минуту будет
     стучаться в несуществующий эндпоинт.
- **Риск при задержке:** нет, ровно наоборот — выкатывать раньше нельзя.
