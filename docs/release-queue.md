# Очередь релиза

Накопитель готовой, но ещё не опубликованной работы. Владелец ведёт несколько
диалогов параллельно, каждый доводит свою фичу до готовности и **останавливается
перед публикацией**; потом всё накопленное уезжает в прод **одним мерджем = одним
билдом Vercel**.

Правила работы с этим файлом — в `CLAUDE.md`, раздел "Очередь релиза". Коротко:

- сессия дописывает СВОЮ запись в "Ждут публикации" сверху, на своей ветке,
  и на этом заканчивает — в `oodobu` ничего не пушит;
- публикующая сессия собирает все перечисленные ветки в одну релизную,
  прогоняет сборку и открывает ОДИН PR в `oodobu`;
- после публикации записи переезжают в "Опубликовано" (внизу), не удаляются.

Конфликт в этом файле при мердже (две сессии дописали сверху) разрешается как
в журнале — **сохранять обе записи**, не выбирая сторону.

## Ждут публикации

Формат записи:

```
### <ветка>
- **Что:** одна строка, что меняется с точки зрения владельца
- **Проверено:** чем (сборка, мок-тест, скриншоты, ручной прогон)
- **Миграции SQL:** применены / нет; какие именно
- **Риск при задержке:** есть/нет и какой
```

### claude/optimistic-newton-y97o9x
- **Что:** счета из писем поставщиков попадают в базу сами, без ручного
  "Подтвердить" — цена, позиции, ИНН и файл записываются в карточку
  поставщика (и отдельной строкой КП) прямо на приёме письма, ещё до того,
  как его кто-то открыл. В переписке вместо кнопки подтверждения — плашка
  "записано автоматически" с необязательной сверкой позиций со сметой и
  откатом, если система приняла за счёт что-то другое. Попутно три реальных
  пробела распознавания: .xlsx-счета не читались вовсе; кандидатом на
  распознавание брался ПЕРВЫЙ подходящий файл письма, из-за чего картинка
  из подписи отправителя закрывала настоящий счёт рядом (реальный случай —
  "RE: Краска интерьерная", счёт на 2,3 млн ₽ не распознался); вложение без
  имени сохранялось как `attachment.bin` и не распознавалось никогда (теперь
  расширение достраивается из content_type).
- **Проверено:** `npx tsc -b` и `npm run build:app` чистые; мок-тест новых
  блоков переписки (Playwright, скриншот); живой прогон бэкофилла по
  реальной базе — распознано и записано 5 счетов, повторный прогон
  идемпотентен (0 записей).
- **Миграции SQL:** нет, схема не менялась. Но в БАЗУ данные уже записаны
  (см. ниже) — это не миграция, а бэкофилл.
- **Что уже применено к живой базе:** прогнан `scripts/backfill-invoice-
  recognition.mjs`. Записаны счета: КраскиТорг 2 319 610 ₽ (ИНН
  550510437971), Подноги — два счёта по 1 392 660,8 ₽ (ИНН 5032382560).
  Формат записи совместим со старым кодом: `extraction.status` = `confirmed`
  (прод покажет привычную пометку "Данные в базе"), новые поля
  `appliedAutomatically`/`applied` старый фронт просто игнорирует.
- **Риск при задержке:** ограниченный, но есть — пока релиз не опубликован,
  автозапись работает ТОЛЬКО для писем, разобранных бэкофиллом вручную:
  новые входящие письма на проде по-прежнему кладут распознавание в
  `pending` и ждут кнопки. То есть ради свежих счетов бэкофилл придётся
  запускать повторно (он для этого и сделан идемпотентным).
- **Конфликты при сборке:** `SupplierCorrespondenceTab.tsx` и `Suppliers.tsx`
  (проп `onQuoteAdded` заменён на `onQuotesChange` — если параллельная ветка
  трогала работу с КП в переписке, сводить руками), `docs/session-journal.md`
  и этот файл — как обычно, сохранять обе записи.

### claude/wonderful-einstein-vdg945 — ОТЛОЖЕНА ОСОЗНАННО
- **Что:** очередь повторной отправки одиночных писем (отказ Resend больше не
  теряет письмо): новая таблица `outgoing_email_jobs`, колонки `send_status`/
  `send_error` у `supplier_offer_emails` и `purchase_emails`, Edge Function
  `process-outgoing-emails`.
- **Почему не в релизе 2026-09-12:** в шапке её миграции
  (`supabase/migrations/20260912-outgoing-email-queue.sql`) прямым текстом:
  «эта миграция ещё НЕ применена к проду (владелец попросил не выкатывать до
  обновления тарифа)». Проверено запросом к базе — таблицы
  `outgoing_email_jobs` там действительно нет, то есть код бы поехал в прод
  и обращался к несуществующей таблице.
- **Что нужно для публикации (все три шага, по порядку):**
  1. обновить тариф Resend (ради этого и откладывалось);
  2. применить миграцию, затем задеплоить Edge Function
     `process-outgoing-emails`;
  3. только ПОСЛЕ деплоя функции раскомментировать и выполнить блок
     `cron.schedule` в конце той же миграции — иначе крон каждую минуту будет
     стучаться в несуществующий эндпоинт.
- **Риск при задержке:** нет, ровно наоборот — выкатывать раньше нельзя.
