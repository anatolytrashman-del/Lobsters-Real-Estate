# Автоматическое расширение каталога поставщиков (с 2026-09-12)

Владелец, 2026-09-12: «Раз у нас есть категории, стоит пойти в глубь и расширить
список поставщиков по каждой категории... В идеале — через самых дешёвых агентов
прям внутри клода... В идеале настроить всё так, чтобы процесс шёл фоново,
вне зависимости от того, открыт ли мой комп и клод код — я усну, процесс
фоново выполнится, а утром синхронизируется». Только Москва или представительство
в Москве. Категория «Оснащение и услуги» — не берём. Цель — не менее 50
поставщиков «своих» на категорию (не считая баз/гипермаркетов).

Это НЕ старый пайплайн `supplier_web_search_jobs`/ProxyAPI (~195₽/задание,
`process-supplier-jobs`) — тот шёл по уже заведённым карточкам поставщиков
(обогащение контактов). Здесь наоборот: ищем НОВЫХ поставщиков через субагентов
Claude (`Agent`, `model: "haiku"` — самая дешёвая модель харнесса) с доступом
к WebSearch/WebFetch.

## Механизм фонового прогона

Сессия — облачная (Claude Code Remote), поэтому «фоново, вне зависимости от
компа» решается через Routine (`create_trigger`, самопривязанный к этой же
сессии, id `trig_01P4x2FWHfoA2HrfpuEWbLAk`, cron `1 * * * *` — раз в час,
сервер сам привязывает к минуте создания). Раз в час — не выбор, а потолок
платформы: `update_trigger` на `*/5 * * * *` вернул явную ошибку «minimum
interval is 1 hour» (проверено 2026-09-12). Каждое срабатывание:
1. Читает этот файл, берёт следующую категорию из очереди со статусом `в работе`
   или первую `не начата`.
2. Догоняет её до 50 (или до явного «выдохлась» — см. ниже).
3. Правит таблицу очереди ниже, коммитит и пушит изменения в файле в ветку сессии.
4. Если очередь пуста — сообщает владельцу и не пересоздаёт триггер (одно из
   срабатываний должно вызвать `delete_trigger` на саму себя).

## Как ищем и вставляем (протокол на каждую категорию)

1. Взять `includes`/`supplyGroups` категории из `src/data/supplierCatalog.ts` —
   это и есть бриф для агентов (что считается «этой категорией»).
2. Свежий список уже существующих доменов — одним SQL-запросом
   (`select website_url from supplier_research_offers where website_url is not null`),
   не хардкодить старый список — за час список меняется.
3. Параллельно (в одном сообщении) 6–10 вызовов `Agent` с `model: "haiku"`,
   каждому — задание найти 5–8 РАЗНЫХ поставщиков категории через WebSearch:
   реальная компания (не маркетплейс, не агрегатор, не ОптЛист/Optostroy —
   те отдельно, «Площадки»), Москва или представительство в Москве
   (юрадрес/склад/шоурум/«доставка по Москве» на самом сайте — не гадать по
   уставной форме, а видеть текст на сайте), рабочий email для заказов (не
   info@ на деревню, реальный отдел продаж/опт), сайт. Явно указать агенту:
   не изобретать данные, только то, что реально нашёл по ссылке; если email
   не нашёлся — оставить пустым, не выдумывать.
4. Свести ответы, отсеять дубли (домен уже есть в базе ИЛИ совпадает с другим
   агентом в этом же прогоне).
5. INSERT — по одной строке за раз через Management API (классификатор
   блокирует групповые операции, см. CLAUDE.md/журнал 2026-09-12): `request_id`
   = id строки `supplier_research_requests` с `title`, ТОЧНО равным названию
   категории (все 23 строки уже заведены — переименование легаси и довозданные
   недостающие сделаны в этом же заходе), `country = 'Россия'`, `city = 'Москва'`,
   `verified = false`, `contact_source = 'ai-research-2026-09'` (тег, чтобы
   отличать от ручного ввода и от ProxyAPI-обогащения).
6. Обновить счётчик в таблице ниже.

«Выдохлась» — если два прогона подряд на категорию дают < 3 новых (после
дедупа) — пометить статусом `выдохлась (N/50)` и идти дальше по очереди, не
зависать на одной категории вечно.

## Технический след этого захода (2026-09-12, для будущих сессий)

- Применена ранее отложенная миграция переименования 10 легаси-строк
  `supplier_research_requests` под новые названия категорий (файл
  `supabase/migrations/20260912-supplier-catalog-rename.sql` уже лежал в
  репозитории, просто не был применён) — по одной строке за раз, классификатор
  пропустил все 10.
- Довозданы 13 строк `supplier_research_requests` под категории без своего
  запроса — иначе `findCatalogCategory` (сопоставление по title) их не видел
  бы, и агентам было бы некуда вставлять поставщиков без кроула сайта.
- Добавлена колонка `supplier_research_offers.city` (text, nullable) —
  раньше был только `country`, фильтр «Москва или представительство» не на
  чем было делать. Обратной миграции для старых 275 строк НЕ делали — city
  у них остаётся пустым, это не ломает старую логику (страна по-прежнему
  первична для существующих фильтров).
- Ловушка при INSERT: `price` у `supplier_research_offers` — NOT NULL без
  дефолта (в отличие от большинства текстовых полей, у которых дефолт
  `''`/`'[]'`). У 263 из 275 старых строк `price = 0` — это и есть конвенция
  «цена не указана», использовать её же, иначе INSERT падает с `23502 null
  value in column "price"`.
- Уточнение критерия «Москва»: город Московской области (Подольск,
  Железнодорожный, Люберцы и т.п.) САМ ПО СЕБЕ не считается — нужна ЯВНАЯ
  цитата про представительство/склад/доставку именно в Москве. Просто
  «рядом с Москвой» — недостаточно (2026-09-12, категория «Электромонтаж»:
  исключены 2 находки с адресом только в области, без цитаты про Москву).
- Разовый сбой у одного из 4 агентов (категория «Электромонтаж»,
  2026-09-12): один агент сообщил, что прокси заблокировал WebFetch на

  прокси, не системное ограничение. Данные из того угла всё равно вставил
