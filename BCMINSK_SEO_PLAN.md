## Порядок внедрения (по документу)

1. Хаб-страницы (район/метро/класс) — структурный фундамент.
2. Сводка по рынку в каталоге + текстовое описание в карточках.
3. FAQ + schema.org на обоих типах страниц.
4. Транспорт, карта, техпараметры, ставки в карточке.
5. Сравнение, подборки, плюсы/минусы, инвестиционный блок.

## Блокеры / решения, нужные от владельца

- **Метро как структурное поле.** Сейчас `metro` — одна свободная строка.
  Чтобы делать хабы "по станции метро" (пункт 2 каталога, пункт 3 карточки
  — точное "650 м, 8 минут" вместо текста), нужно либо распарсить станцию
  из существующего текста в отдельное вычисляемое поле, либо завести
  отдельную колонку в БД и заполнить руками/повторным ресерчем. Точные
  метры/минуты у большинства новых 118 записей просто НЕТ (prometr.by даёт
  только грубые категории "шаговая доступность"/"более 3 остановок") — их
  взять неоткуда без ручной сверки по каждому зданию (как уже делалось для
  части исходных 27 через веб-архивы Яндекс.Карт, которые присылал
  владелец) — это отдельная большая задача, не пятиминутная правка.
- **Описание в прозе (300-600 слов) на карточке** — приоритет 1 пункт 1
  для карточки, но требует настоящего ресерча по каждому БЦ (история,
  архитектура, для кого подходит), чтобы не быть шаблонным текстом
  (ровно то, от чего сам документ предостерегает — "не 'портал
  предлагает', а полезное"). У исходных 27 уже ЕСТЬ насыщенные
  `highlights` (история/арендаторы/награды из ресерча) — для НИХ описание
  можно частично собрать из уже добытых фактов. Для новых 118 (только из
  prometr.by, без ресерча) — писать текст не из чего, кроме структурных
  полей (адрес/класс/площадь) — риск получить именно тот шаблонный текст,
  которого нужно избегать. **Спросить владельца перед стартом**: делать ли
  масштабный ресерч по 118 зданиям (много сессий), или ограничиться
  честным кратким автосоставленным абзацем из структурных полей без
  претензии на «300-600 слов редакционного текста».
- **Дерево хаб-URL по пересечениям параметров** (класс×район, класс×метро
  и т.п., предложено владельцем 2026-09-06) — до реализации: посчитать
  реально непустые комбинации по данным (не создавать хаб для комбинации
  без единого БЦ — риск тонкого контента), решить URL-схему
  (`/minsk/bcminsk/class/a/raion/oktyabrsky` и т.п.) и её SEO-обвязку на 3
  уровня breadcrumb. Ждёт метро-поля (см. выше), если нужны и metro-хабы
  в пересечении.
- **Ставки аренды** — структурных данных по ставкам на уровне каталога нет
  вовсе (есть только у части отдельных БЦ через "Объявления с Kufar и
  Realt"). Пункты про диапазон ставок (каталог) и "ставки и динамика"
  (карточка) невозможны без нового источника данных — не начинать без
  явного решения, откуда брать цифры.
